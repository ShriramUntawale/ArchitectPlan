From consistent hashing to reliable money transfers

We started with one question: how should NGINX route millions of users to Spring Boot servers? That led to a deeper problem: how do multiple application instances, databases, and Kafka consumers cooperate without losing or duplicating money?

The answer is a set of separate guarantees. Each mechanism solves one failure mode. None solves the entire system by itself.

1. Keep requests stable when servers change

Ordinary hashing often uses hash(key) % serverCount. When the server count changes, most mappings can change. Consistent hashing places keys and server positions on a fixed ring. Adding one server moves only keys it newly owns. Virtual nodes spread ownership more evenly.

Production NGINX uses its own consistent-hash continuum. This simplified demo shows the ownership rule.
upstream app_backend {
  hash $http_x_device_id consistent;
  server app1:8080;
  server app2:8080;
  server app3:8080;
}

NGINX chooses an application server, not a database shard. Stable routing helps local caches, but it does not copy state from a failed application instance.

2. Scaling Spring Boot does not scale the database

All application instances may still send queries to one PostgreSQL primary. Optimize queries first. Cache frequently read data. Read replicas can share read traffic, while sharding splits ownership of data across databases.

A replica can be behind the primary. Reading from the fastest replica does not necessarily return the latest write.

3. Fresh reads need proof, not a guess

After a user changes their profile, a replica might still contain the old value. A five-second Redis recent-write marker can route reads to the primary, but a fixed TTL is only a heuristic. For stronger read-after-write behavior, use a durable version or WAL freshness requirement, and only read from a replica that has caught up.

Redis can share routing hints across Spring Boot instances. But if an application crashes after committing PostgreSQL and before updating Redis, that hint may be missing. Critical reads need a safe fallback, often the primary.

4. A timeout is not proof of failure

A client submits a transfer, PostgreSQL commits it, and the application crashes before replying. Retrying with a new key could transfer money twice. Use a stable idempotency key, a database uniqueness constraint, and atomic transaction handling. The same key with the same payload resolves to the original operation; a conflicting payload is rejected.

For concurrent requests, checking if a key exists before acting is unsafe. Two application instances can both observe absence. The unique constraint and transaction must make claiming the key and applying the business effect atomic.

5. One transaction cannot cover two independent shards by default

When Account A and Account B live in separate PostgreSQL databases, ordinary Spring @Transactional does not automatically make both commits atomic. Two-phase commit coordinates them, but can block and hold resources. A Saga commits local steps independently and recovers through retries or compensation. It therefore exposes intermediate states unless the business interface hides them.

6. The hardest case: credit and cancellation race

Suppose crediting Account B is delayed. The coordinator times out and wants to refund Account A. A late credit might still arrive. If both happen, money is created. A dead-letter queue does not make late replay safe.

The Credit Service needs a durable operation row with a unique transfer ID. Both credit and cancellation try to change PENDING to a mutually exclusive terminal state. PostgreSQL conditional updates serialize the race. The winning credit must atomically update the balance and outbox. Cancellation must durably prevent future credit before the coordinator refunds.

UPDATE transfer_operations
SET status = 'CREDITED'
WHERE transaction_id = 'TXN-123'
  AND status = 'PENDING';

Cancellation uses the same condition but sets CANCELLED. Only one can update the row. If a credit has already committed, a refund must not proceed merely because a failure event arrived later. If cancellation wins, the Credit Service must reject late credit requests.

The core design rule: transport delivery is not business completion. Business state must be durable, idempotent, and protected by valid atomic transitions.

Interview recap

NGINX consistent hashing stabilizes request ownership. Read replicas reduce read pressure but introduce stale reads. Sharding spreads data but creates cross-database transactions. Idempotency prevents duplicate business effects. Transactional outbox protects event publication. Saga coordinates local commits. A durable state machine, atomic credit-versus-cancel decision, and reconciliation keep delayed events from creating or losing money.

Three questions to ask in any distributed design

What if a process crashes immediately after commit? What if the same event arrives twice? What if success and cancellation arrive in the opposite order?
