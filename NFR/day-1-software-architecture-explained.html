SOFTWARE ARCHITECT TRANSITION · DAY 1

Architecture through failure

Our case study is a Spring Boot order API backed by Kafka and PostgreSQL. The central lesson: an architecture is a set of guarantees and trade-offs, not a collection of technologies.

A developer implements order creation. An architect asks what happens when the client retries, the database fails, or traffic increases 100 times. Start with measurable requirements before choosing Kafka, Redis, Kubernetes, or replicas.

Accepting is not completing

The API can durably publish an order event to Kafka and return 202 Accepted. That means the request is queued for processing, not that the order is persisted or fulfilled. A Location URL can expose status, but that status endpoint needs a queryable source.

Notice that Kafka acknowledgment happens before the database commit. If PostgreSQL is down, ACCEPTED can remain the business state while operational metadata tracks retries. A separate status store can improve query availability, but introduces another consistency problem. We decided not to add one without a business requirement.

Why an offset is not a database transaction

Kafka remembers the next position for a consumer group within each partition. PostgreSQL commits its own transaction separately. A crash can occur between the two commits.

The solution is at-least-once delivery with idempotent database effects. Put a unique event ID and the business write in the same PostgreSQL transaction. The database uniqueness constraint, not a Java check alone, prevents concurrent duplicates.

BEGIN;
INSERT INTO processed_events(event_id)
VALUES ('evt-101')
ON CONFLICT DO NOTHING;
-- Only insert the order if event was new.
INSERT INTO orders(id) VALUES ('ORD-101');
COMMIT;

Illustrative SQL sequence. Production code must condition the order insert on successful marker insertion and commit both changes atomically.

When a batch contains a poison event

Imagine 100 events in a database transaction. Event 50 violates a constraint. Retrying the unchanged batch will fail forever. Isolate the record-specific failure, process valid records idempotently, and publish the invalid record to a dead-letter topic (DLT).

100 events waiting

The entire batch is initially unprocessed.

Do not commit the source offset past event 50 until the invalid event has been durably handled. If the DLT acknowledgment is lost, publication may have succeeded, so the DLT consumer must also be idempotent. Use source topic, partition, and offset as a stable identity. Offset commits are partition-specific and must reflect contiguous completed progress.

Backpressure during recovery

Kafka buffers bursts but does not make PostgreSQL faster. After an outage, incoming orders continue while the backlog drains. Consumer rate must stay within the database's measured sustainable capacity, leaving headroom for other traffic.

Net drain: 133 orders/sec

Formula: time = backlog / (consumer rate - arrival rate). If arrivals match or exceed consumption, the backlog never clears. Connection pools cap concurrency, not database write rate. Batch size, consumer concurrency, retry pacing, and throughput limits must be tuned together.

Turn business language into NFRs

A functional requirement says customers can place orders. A non-functional requirement (NFR) states how quickly, reliably, securely, and at what scale that must work. Numbers should come from business forecasts, observed usage, user expectations, and measured system behavior.

Peak = daily orders × peak share ÷ 7,200 seconds. This is order throughput, not total API RPS.

Latency is a different requirement. If customers need confirmation within one second, allocate a response budget across network, API, broker acknowledgment, and UI, then validate end-to-end measurements. A p95 of 200 ms means roughly 95% of requests finish within 200 ms. It does not follow automatically from an RPS estimate.

Targets such as 200 ms p95 or 99.95% availability are proposals until the business accepts them. Define the workload, percentile, measurement window, and failure assumptions.

Check your architecture instincts

1. PostgreSQL is unavailable for 30 minutes. Should every pending order go to a DLT?

2. Both consumers check whether an event exists and see 'no'. What prevents duplicate writes?

3. Consumer rate is 250/s and new arrivals are 300/s. Will backlog drain?

The Day 1 takeaway: Start with the business requirement, derive a measurable guarantee, identify failure windows, and choose the simplest architecture that meets those guarantees. Next: refine p95 latency targets and test architecture trade-offs with load and failure experiments.
